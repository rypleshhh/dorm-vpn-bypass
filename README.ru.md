# Обход DPI в общаге — Selective Routing через VLESS+Reality (включая UDP)

Личная конфигурация для обхода фильтрации в сети общежития, которая
блокирует **весь UDP** и делает глубокую инспекцию пакетов (DPI) для TCP.
Работает на роутере OpenWrt с выборочной маршрутизацией, поверх одного
VPS с Xray-core.

Это не готовый инсталлятор — реальная рабочая личная конфигурация,
выложенная как референс. IP, домены и подсеть LAN нужно будет
подставить свои.

## Зачем это нужно

- Сеть общежития полностью блокирует UDP (не проходит ни QUIC, ни
  WireGuard, ни hysteria2 — вообще ничего).
- TCP/443 тоже фильтруется по DPI, поэтому обычный трафик режется/
  троттлится по SNI или по протокольному отпечатку.
- Цель: маршрутизировать через VPS только конкретный трафик
  (заблокированные на российском рынке сайты, Telegram, а теперь и
  UDP-приложения вроде Steam/Discord), а весь остальной трафик пускать
  напрямую — с минимальной добавленной задержкой и без настройки на
  каждом устройстве отдельно (один раз на роутере).

## Архитектура

```
LAN-клиент
  |
  v
dnsmasq резолвит домен --> nft set (russia4 / telegram4)
  |
  v
nftables prerouting:
  - TCP/443, попадающий в эти сеты --> REDIRECT --> Xray dokodemo-door :12345
  - ВЕСЬ UDP (кроме порта 53)      --> TPROXY   --> Xray dokodemo-door :12346
  |
  v
Xray (роутер)
  - TCP-путь  --> VLESS+Reality outbound "proxy"     (включён mux)
  - UDP-путь  --> VLESS+Reality outbound "proxy-udp" (без mux — см. ниже)
  |
  v
VPS (Xray inbound, VLESS+Reality на TCP/443)
  |
  v
Интернет
```

Оба outbound'а смотрят на один и тот же VPS/порт — Xray просто
поднимает к нему два независимых TCP+Reality тоннеля.

### Почему TCP и UDP сидят на разных Xray inbound'ах

Изначально был один inbound `dokodemo-door` для обоих. Включение
`sockopt.tproxy` на нём (нужно для UDP) ломало резолвинг
`SO_ORIGINAL_DST` для TCP-пути, потому что REDIRECT (DNAT) и TPROXY —
разные механизмы ядра, которые не уживаются на одном сокете.
Симптом: Xray "тоннелировал" запросы сам на себя вместо реального
адреса назначения. Фикс: два inbound'а на двух портах, TCP остаётся на
REDIRECT, UDP получает свой отдельный inbound на TPROXY.

### Почему TCP и UDP сидят на разных outbound'ах (и mux только у одного)

`mux.cool` мультиплексирует множество логических потоков через одно
физическое TCP-соединение к VPS — отлично убирает повторный оверхед
TLS/Reality handshake при веб-сёрфинге (см. ниже). Но это же значит,
что потеря ОДНОГО пакета блокирует ВСЕ потоки, разделяющие это
соединение (head-of-line blocking). Для браузера, грузящего десяток
ресурсов, это нормально; для чего-то вроде игрового UDP-трафика,
постоянно открывающего и закрывающего короткие потоки — плохо. Поэтому
веб-трафик (TCP) идёт через outbound с mux, а UDP (игры/войс) — через
второй, без mux, чтобы потоки оставались независимыми.

### Flow: `xtls-rprx-vision` против `none`

`xtls-rprx-vision` даёт TLS padding/splicing, который помогает прятать
паттерны XTLS-трафика от продвинутого DPI, но он **несовместим** с
`mux.cool` (mux заворачивает трафик в свой протокол, что ломает
предположения vision о сыром TLS-потоке — на стороне сервера декодинг
ответа падает с ошибкой EOF). Мы полностью убрали `flow` (и на роутере,
и на VPS — должно совпадать на обеих сторонах), чтобы разрешить mux,
пожертвовав этим конкретным свойством анти-фингерпринтинга ради
большого выигрыша в задержке: время хендшейка первого соединения упало
с ~0.43с до ~0.11с, как только mux начал переиспользовать уже прогретое
соединение вместо полного TCP+TLS+Reality хендшейка на каждый новый
домен. Это осознанный компромисс — приемлемый для обхода обычной
DPI-блокировки, но не рассчитанный на противостояние активному
продвинутому детекту.

### Тоннелирование UDP (Steam/Deadlock/Discord и т.д.)

Весь UDP из LAN (кроме DNS на порту 53, который явно исключён, чтобы
не заворачивать локальный резолвинг в тоннель) перехватывается TPROXY и
тоннелируется через VLESS на VPS, откуда уходит наружу через обычный
`freedom` outbound. Фильтрации по конкретным приложениям/IP нет — IP
серверов Steam Datagram Relay динамические, их не имеет смысла
перечислять.

Известное ограничение: это UDP-over-TCP по своей конструкции (VLESS
сам заворачивает UDP-фреймы внутрь своего TCP-потока), поэтому
наследует head-of-line blocking, свойственный TCP. Игра вроде Deadlock,
которая гоняет много коротких UDP-потоков (пробинг relay-серверов,
матчмейкинг), будет давать больше джиттера, чем один долгий UDP-поток
(например, тоннель WireGuard) — просто из-за механизма тоннелирования,
а не из-за неправильной настройки роутера. Также пробовались и не
помогли:
- **TCP Fast Open** (на обеих сторонах, `sockopt.tcpFastOpen`) —
  без измеримого эффекта, поскольку почти вся задержка сидит в
  хендшейке Reality/TLS, а не в TCP SYN.
- **Оборачивание в духе `udp-over-tcp`** — то же фундаментальное
  ограничение, что и выше, лишний хоп смысла не имеет.

Единственный реальный оставшийся рычаг для более низкой и стабильной
игровой задержки — VPS географически ближе к реально используемым
игровым серверам, но это уже инфраструктурное решение, а не вопрос
конфига.

## Структура

```
router/etc/xray/config.json           Конфиг Xray (сторона OpenWrt)
router/etc/init.d/xray-nft            Таблица TCP-редиректа + автообновление IP-листа Telegram
router/etc/init.d/xray-nft-udp        Таблица UDP TPROXY + policy routing, переживает ребут
router/etc/init.d/russia-inside-update  Еженедельное обновление списка доменов (itdoginfo/allow-domains)
router/etc/sysctl.d/99-tcp-fastopen.conf
vps/etc/xray/config.json              Конфиг Xray (сторона VPS)
vps/etc/systemd/system/xray.service   Стандартный systemd unit для xray-core
vps/etc/sysctl.d/99-tcp-fastopen.conf
docs/troubleshooting.ru.md            Проблемы, с которыми столкнулись при настройке, и как их диагностировали
```

## Установка

### VPS

1. Установить xray-core (официальный установочный скрипт с
   [github.com/XTLS/Xray-install](https://github.com/XTLS/Xray-install)).
2. Сгенерировать пару ключей Reality: `xray x25519` (даст приватный и
   публичный ключ) и UUID: `xray uuid`.
3. Придумать `shortId` (любая короткая hex-строка, например
   `openssl rand -hex 8 | cut -c1-16`) и домен для маскировки, который
   реально отдаёт TLS 1.3 и не заблокирован по гео для IP твоего VPS
   (здесь использовался `www.idealo.de`, подбери свой и проверь через
   `openssl s_client`).
4. Скопировать `vps/etc/xray/config.json`, подставить `YOUR_UUID`,
   `YOUR_REALITY_PRIVATE_KEY`, `YOUR_SHORT_ID`.
5. Скопировать `vps/etc/systemd/system/xray.service`,
   `systemctl daemon-reload`, `systemctl enable --now xray`.
6. Скопировать `vps/etc/sysctl.d/99-tcp-fastopen.conf`, применить
   `sysctl -p`.
7. Открыть порт 443 в файрволе.

### Роутер (OpenWrt)

Протестировано на OpenWrt 24.10.3, ramips/mt7621 (ASUS RT-AX53U).
Поправь `LAN_NET` в init-скриптах, если твоя LAN не `192.168.1.0/24`.

1. Установить xray-core под архитектуру роутера, `kmod-nft-tproxy` и
   `dnsmasq-full` (стоковый `dnsmasq` не умеет `nftset` — сначала
   удали обычный `dnsmasq`).
2. Скопировать `router/etc/xray/config.json`, подставить `YOUR_VPS_IP`,
   `YOUR_UUID`, `YOUR_REALITY_PUBLIC_KEY`, `YOUR_SHORT_ID` (должны
   совпадать со значениями на VPS).
3. Прописать `confdir='/etc/dnsmasq.d'` в UCI-конфиге dnsmasq
   (`uci set dhcp.@dnsmasq[0].confdir='/etc/dnsmasq.d'; uci commit dhcp`).
4. Скопировать `router/etc/init.d/xray-nft`, `xray-nft-udp` и
   `russia-inside-update` в `/etc/init.d/`, сделать `chmod +x`, и
   `enable` все три (`/etc/init.d/<name> enable`).
5. Скопировать `router/etc/sysctl.d/99-tcp-fastopen.conf`, применить
   `sysctl -p`.
6. Один раз выполнить `/etc/init.d/russia-inside-update restart`, чтобы
   заполнить список доменов, затем `/etc/init.d/xray-nft restart`, чтобы
   заполнить IP-сет Telegram, затем запустить Xray и оба
   nftables-скрипта.
7. Настроить еженедельный cron для списка доменов:
   `30 7 * * 1 /etc/init.d/russia-inside-update restart >/tmp/russia-inside-update.log 2>&1`
8. Один раз перезагрузить роутер и убедиться, что всё поднимается само
   — что именно проверять см. в `docs/troubleshooting.ru.md`.

## Что не входит в репозиторий

- Сам файл `russia-inside.conf` для dnsmasq — он скачивается и
  генерируется скриптом `russia-inside-update`, его не редактируют
  руками и не коммитят.
- Реальные секреты (UUID, ключи Reality, IP VPS) — никогда не коммить
  их. Держи заполненные реальными значениями `config.json` вне git (см.
  `.gitignore`) или в отдельном приватном месте.
